## โจทย์ที่ยากกว่าที่คิด

ประมวลกฎหมายที่ดินไม่ใช่เอกสารเดียว แต่คือกฎหมายเล่มเดียวที่มี **53 สถานะเวลา**
(ฉบับดั้งเดิม พ.ศ. ๒๔๙๗ + ฉบับแก้ไข ๑๕ ฉบับ + ฉบับรวมสะสม ๒๐ ช่วงเวลา)

ความยากไม่ใช่ "หาไม่เจอ" แต่คือ **"เจอหลายฉบับแล้วต้องเลือกฉบับที่ใช้บังคับอยู่จริง"** —
ถามว่า _"ที่ดินใบจองห้ามโอนกี่ปี"_ ระบบเจอคำตอบใน ๕ ฉบับ ฉบับเก่าบอก ๕ ปี ฉบับปัจจุบันบอก ๑๐ ปี
เลือกผิด = ตอบด้วยกฎหมายที่ยกเลิกไปแล้ว

**แนวคิดหลัก — ข้อเท็จจริงให้โค้ดคำนวณ การเรียบเรียงให้ LLM**
งานกฎหมายรับ "ส่วนใหญ่ถูก" ไม่ได้ สายการแก้ไขกฎหมายจึงอ่านจากตัวบทด้วยโค้ด (ถูก ๑๐๐% ตรวจสอบได้
ชี้ได้ว่ามาจากไฟล์ไหน) ไม่ให้ LLM เดา ส่วน LLM มีหน้าที่เรียบเรียงคำตอบจากข้อเท็จจริงที่คำนวณมาแล้วเท่านั้น

## สถาปัตยกรรม

**ตอนสร้างดัชนี (ทำครั้งเดียว)**
```
PDF ──PyMuPDF──> chunk ตามขอบ "มาตรา/ข้อ" ──> Chroma (semantic) + BM25 (ตัดคำไทยด้วย newmm)
  └─ หน้าสแกน ──EasyOCR──┘                 ├──> amendment graph  (มาตราไหนถูกแก้โดยใคร)
                                            └──> entity index     (ใคร/เอกสารอะไร อยู่มาตราไหนบ้าง)
```
> ทั้ง **amendment graph** และ **entity index** คำนวณด้วยโค้ดล้วน (regex + การนับ) ไม่มี LLM เกี่ยว
> จึงครบถ้วนและรันซ้ำได้ผลเดิมทุกครั้ง — ครอบคลุมตัวบท 34/131 และ 69/131 มาตราตามลำดับ

**ตอนตอบคำถาม**
```
ถาม ──> rewrite คำถามต่อเนื่อง (ถ้ามีประวัติแชท)
     │
     ├─ เป็นคำถามประวัติ/เปรียบเทียบ + ระบุเลขมาตรา?  (กฎในโค้ด ไม่ใช่ LLM)
     │    └─ ใช่ ──> 🔵 เดินกราฟ (article_chain + timeline) ──> LLM เรียบเรียง
     │
     └─ ไม่ใช่ ──> เลือกกลุ่มเอกสาร/ปี (กฎในโค้ด) ──> แตกคำค้น 4 มุม
                ──> hybrid retrieve (semantic + BM25 รวมอันดับด้วย RRF)
                ──> ยุบเวอร์ชันซ้ำ ──> rerank 50→12
                ──> 🟢 เติมข้อเท็จจริงที่คำนวณไว้ (สรุปฉบับ / บทบาทกรรมการ)
                ──> LLM ตอบ
```

<details>
<summary>ศัพท์ที่โผล่ในแผนภาพ (กดดู)</summary>

- **semantic** — ค้นด้วยความหมาย ถามคนละคำแต่ความหมายใกล้กันก็เจอ
- **BM25** — ค้นด้วยคำตรง ๆ เก่งเรื่องเลขมาตรา/ชื่อเฉพาะที่ semantic มักพลาด
- **newmm** — ตัวตัดคำไทยของ pythainlp · ภาษาไทยไม่เว้นวรรค ถ้าไม่ตัดคำ BM25 ทำงานไม่ได้
- **RRF** (Reciprocal Rank Fusion) — สูตรรวม *อันดับ* จากสองการค้นเข้าด้วยกัน `1/(60+อันดับ)`
  ใช้อันดับแทนคะแนนดิบ เพราะคะแนนของ semantic กับ BM25 คนละสเกล เทียบกันตรง ๆ ไม่ได้
- **rerank 50→12** — เอา 50 ก้อนแรกให้โมเดล cross-encoder อ่านคู่กับคำถามทีละก้อน
  แล้วคัดเหลือ 12 · แม่นกว่าแต่ช้า จึงใช้เป็นด่านสองไม่ใช่ด่านแรก
</details>

> ⚠️ **การเลือกเส้นทางทั้งหมดใช้กฎในโค้ด ไม่ใช่ให้ LLM ตัดสิน** — เพราะ "กฎหมายฉบับไหน
> ใช้บังคับอยู่" เป็นข้อเท็จจริง ไม่ใช่เรื่องตีความ ถ้า router เดาพลาด = ตอบด้วยตัวบทที่ยกเลิกแล้ว
> เรียกวิธีนี้ว่า **Hybrid RAG + rule-based routing + graph** (ไม่ใช่ agent และไม่มีการวนค้นซ้ำ)

### จุดที่ต้องระวัง

- **ห้ามใช้ pdfplumber คัดข้อความไทย** — มันเรียงตาม x-coordinate ทำให้สระ/วรรณยุกต์
  หลุดตำแหน่ง (`"ทรพั ยส์ นิ"` แทน `"ทรัพย์สิน"`) พังทั้ง embedding, BM25 และตัวบทที่ LLM คัดไปตอบ
- **เลขไทย ๐-๙** ถูก normalize เป็นอารบิกตอน tokenize → ถาม "มาตรา 9" เจอ "มาตรา ๙"
- เปลี่ยน `CHUNK_SIZE` / `EMBED_MODEL` ต้อง rebuild: `python -c "import rag; rag.build_vectorstore(force=True)"`
- เปลี่ยนแค่ **วิธีคำนวณ metadata** (ไม่ได้แตะตัวข้อความ) ไม่ต้อง embed ใหม่ทั้งชุด —
  `python -c "import rag; rag.refresh_metadata()"` อัปเดตเฉพาะ metadata ใน Chroma (เร็วกว่ามาก)
- reranker ใช้ GPU ตัวเดียว → FastAPI ต้องรัน **worker เดียว** (อย่าใช้ `--workers >1`)

## metadata ที่เก็บต่อ chunk

ทุก chunk ถูกประทับข้อมูลประจำตัว **ตั้งแต่ตอนสร้าง** — ระบบอ่านทีละไฟล์ ก้อนที่เกิดจากไฟล์ไหน
ได้ข้อมูลของไฟล์นั้นทันทีในลูปเดียวกัน (ไม่ใช่เดาย้อนหลัง) แล้วเก็บลง Chroma คู่กับ vector
ป้ายพวกนี้คือฟิลเตอร์ที่ทำให้ตอบถูกฉบับ: **สิ่งที่ติดตอนเข้า = สิ่งที่ใช้กรองตอนออก**

รหัสประจำก้อน: `id = ชื่อไฟล์::ลำดับ` (เช่น `LandCode2497_Update-vlast_TruePDF.pdf::0003`)
— เห็น id เดียวก็ย้อนถึงต้นทางได้ + metadata อีก 18 ฟิลด์ (`rag._chroma_metadata`):

| กลุ่ม | ฟิลด์ | เก็บอะไร |
|---|---|---|
| **ระบุที่มา** | `source` · `doc_label` | ชื่อไฟล์ · ชื่อเอกสารอ่านง่าย (ใช้แสดงอ้างอิงท้ายคำตอบ) |
| | `page_start` · `page_end` | เนื้อหานี้อยู่หน้าไหนถึงหน้าไหนของไฟล์ |
| | `kind` · `version` · `year` | main/amend/update · เลขฉบับ (vlast→999) · ปีเอกสาร |
| **กรอง/จัดอันดับ** | `in_force` | ⭐ ตัวบทนี้ใช้บังคับอยู่จริงไหม — คำถามปกติกรองด้วยฟิลด์นี้ กันกฎหมายที่ยกเลิกแล้วหลุดมาตอบ |
| | `as_of_year` | ตัวบทสะท้อนกฎหมาย ณ ปีไหน (ตอบคำถามย้อนเวลา) |
| | `group` · `amend_no` | กลุ่มเอกสาร 4 กลุ่ม · รวมการแก้ถึงฉบับที่เท่าไร |
| | `article` | **มาตราหลัก**ของก้อน — ค่าเดียว ใช้จัดอันดับ (ถามเจาะมาตราไหน ก้อนที่ว่าด้วยมาตรานั้นขึ้นก่อน) |
| | `article_nums` | **ทุกมาตราที่โผล่**ในก้อน เช่น `\|8\|9\|10\|11\|` — ใช้ค้นหา (ถามมาตรา ๘ ก้อนนี้ต้องถูกเจอแม้เรื่องหลักคือ ๑๑) |
| **เสริม** | `articles` · `refs` · `section` | ป้ายมาตราแบบเต็ม · มาตราที่ถูกอ้างถึง · หมวด/ภาค |
| | `n_articles` · `is_scan` | จำนวนมาตราในก้อน · มาจาก OCR ไหม (ถูกดันท้ายแถวเพราะเชื่อถือได้น้อยกว่า) |

### ก้อน "กลาง ๆ" ที่ไม่มีหัวมาตรา รู้ได้อย่างไรว่าเป็นมาตราอะไร

98 จาก 106 ก้อนของไฟล์หลักขึ้นต้นกลางความ ไม่มีคำว่า "มาตรา" นำหน้า — ระบบจึงแท็กเป็น**รายบรรทัด**
ตั้งแต่ตอนอ่าน: มีตัวแปรจำว่าบรรทัดนี้อยู่ใต้หัวมาตราไหน ทุกบรรทัดได้ป้ายของตัวเอง พอตัดก้อน:

- `article` (ป้ายหลัก) = มาตราที่**กินเนื้อที่มากสุด**ในก้อน (`dominant_article`)
  ⚠️ ห้ามใช้ "มาตราล่าสุดที่เจอ" — เคยใช้แล้ววัดได้ป้ายผิดถึง 81% เพราะก้อนเดียวคาบหลายมาตรา
- `article_nums` = ทุกมาตราที่โผล่ในก้อน
- ตอน overlap ท้ายก้อนเก่าไปหัวก้อนใหม่ ป้ายบรรทัดถูกยกตามไปด้วย เนื้อความที่ติดมาจึงไม่ลืมสังกัด
- ป้ายรายบรรทัดเป็นนั่งร้านชั่วคราว ใช้สรุปแล้วทิ้ง — **1 chunk มี metadata ชุดเดียวเสมอ**

### ⚖️ ทำไม default ต้องเป็น `vlast` ไฟล์เดียว

กฤษฎีกาไล่ปรับตัวบทให้ทีละมาตราแล้วในฉบับรวมสะสม เทียบทั้งฉบับกับ `Main-v0` ได้ว่า:


`vlast` จึงครอบคลุมทั้ง *"มาตราที่ไม่เคยแก้ → ใช้ของหลัก"* และ *"มาตราที่แก้แล้ว → ใช้ของใหม่"* อยู่ในไฟล์เดียว

ไฟล์ที่เหลือมี **ตัวบทที่ถูกยกเลิกไปแล้วปนอยู่** (เช่น `มาตรา ๙๗` ใน `Main-v0` เป็นเวอร์ชันก่อนแก้)
ถ้าค้นปนกันเมื่อไร = มีโอกาสตอบด้วยกฎหมายที่เลิกใช้แล้ว → `retrieve()` จึงล็อกไว้ที่กลุ่มที่ใช้บังคับเสมอ
การปลดล็อกตัดสิน**ด้วยกฎในโค้ด** (`service.pick_groups`) ไม่ใช่ให้ LLM เดา

นอกจากนี้ยังยุบสำเนาซ้ำ (`_dedupe_versions` — 29% ของดัชนี) และดัน chunk จาก OCR ท้ายแถว (`_demote_scans`)

## การวัดผลและการทดลอง

ทุกการตัดสินใจมีตัวเลขรองรับ ไม่ใช่เดา — ปัจจุบันวัดด้วยคำถามรวม **120 ข้อ ใน 4 แกน**
ผ่าน runner ตัวเดียว (`eval/run_eval.py` ให้คะแนนอัตโนมัติแบบ key-fact matching):

| ชุดคำถาม | วัดแกนไหน | ผลล่าสุด |
|---|---|---|
| `ground_truth.json` (30 ข้อ) | ประวัติการแก้ไข / ย้อนเวลา / เลือกฉบับที่ใช้บังคับ | **28-29/30** — ข้อที่ตกคือข้อที่เฉลยกว้างกว่าคำถาม (ดูด้านล่าง) |
| `ground_truth_v2.json` (30 ข้อ) | อ่านตัวบทสาระให้แม่น: กำหนดเวลา / อัตรา / องค์ประชุม | **30/30** |
| `ground_truth_v3.json` (40 ข้อ) | 4 ระดับรวม**ยากมาก**: เลขเศษส่วน ข้อยกเว้นซ้อน ผลที่สวนสามัญสำนึก | **40/40** (ยากมาก 10/10) |
| `adversarial.json` (12 ข้อหลอก) | **"รู้ตัวว่าไม่รู้"** — ต้องปฏิเสธเมื่อคำตอบไม่มีในเอกสาร ห้ามมโน | **12/12** (ข้อแก้ข้อสันนิษฐานเท็จเคยปรับตัวจับคำ 2 ครั้ง — ระบบตอบถูกทุกรอบจากการตรวจมือ ดู `_note` ในไฟล์) |
| `multihop.json` (8 ข้อ) | **ต้อง hop จริง** — ตอบไม่ได้ถ้าไม่รู้ผลของทอดแรกก่อน | แกนที่ยังไม่สมบูรณ์ ดูหัวข้อการทดลองด้านล่าง |
| `multiturn.json` (6 บทสนทนา · 13 เทิร์น) | **คำถามต่อเนื่อง** — วัด 2 ชั้น: เขียนคำถามใหม่ถูกไหม + คำตอบถูกไหม | คำตอบ **13/13** · การเขียนคำถามใหม่ 6-7/7 (ดูด้านล่าง) |

> "98-99/100" ที่โปรยไว้บนสุด = ผลรวมของ 4 ชุดแรก (30+30+40 มีเฉลย + 12 ข้อหลอกนับแยก)
> ชุด `multihop.json` เขียนขึ้นทีหลังเพื่อ**หาจุดอ่อนของตัวเอง** จึงไม่รวมในตัวเลขนั้น

#### 2 ข้อที่ตก — ระบบตอบถูก แต่เฉลยถามมากกว่าที่คำถามถาม

เคยเขียนไว้ว่า `29/30 รัน 3 รอบ ±0.0` · วัดใหม่ 5 ส.ค. 2569 ได้ **28/30** จึงแก้เป็นช่วง
ตัวเลขเดิมไม่ผิดตอนที่วัด แต่ **"±0.0" เป็นคำที่แรงเกินหลักฐาน** — 3 รอบยังน้อยเกินจะรับประกัน

| ข้อ | คำถาม | ระบบตอบ | เฉลยบังคับให้มี |
|---|---|---|---|
| **E5** | ใครเป็น**ประธาน**คณะกรรมการจัดที่ดิน | รัฐมนตรีว่าการกระทรวงมหาดไทย ✓ | + `อธิบดีกรมที่ดิน` ซึ่งเป็น**เลขานุการ ไม่ใช่ประธาน** |
| **H10** | ฉบับที่ ๔ แก้ทับงานฉบับก่อนหน้าที่มาตราใดบ้าง | ตอบได้ 3 จาก 4 มาตรา | ครบทั้ง 4 (`31/58/69/103`) |

**E5 ที่เคยผ่าน ผ่านเพราะโมเดลบังเอิญตอบยาวจนพ่วงชื่อเลขานุการมาด้วย**
รอบนี้ตอบกระชับตรงคำถามกว่า — แต่ได้คะแนนน้อยลง เท่ากับเทสต์วัดความยาวคำตอบ ไม่ได้วัดความถูก

**จงใจไม่แก้เฉลย** ทั้งที่แก้แล้วตัวเลขจะกลับเป็น 29/30 ทันที — การแก้ข้อสอบให้ตัวเองผ่าน
ทำให้ตัวเลขที่เหลือทั้งหมดเชื่อไม่ได้ไปด้วย · บันทึกไว้ตรง ๆ ดีกว่าได้เลขสวยที่ไม่มีความหมาย

_บทเรียน: ตัวให้คะแนนแบบ key-fact matching วัด "ตอบครบไหม" ได้ดี แต่แยกไม่ออกระหว่าง
"ตอบไม่ครบ" กับ "เฉลยถามเกินคำถาม" — ข้อที่ตกต้องอ่านคำตอบจริงประกอบเสมอ ห้ามดูแต่ตัวเลข_

```powershell
python eval\run_eval.py --mlflow                                   # ชุดหลัก 30 ข้อ
python eval\run_eval.py --file ground_truth_v3.json --mlflow       # ชุดอื่น: ใส่ --file
python eval\run_eval.py --repeat 3                                 # วัดความนิ่ง (LLM ไม่คงที่ 100%)
```

**ตัวอย่างวงจร เจอ → แก้ → ล็อก (ข้อ V23):** วัดรอบแรก _"มาตรา ๓๕ ถูกยกเลิกโดยกฎหมายใด"_ ตก —
ระบบตอบว่าหาไม่เจอ (ไม่มโน ✓) ทั้งที่คำตอบ (ปว.๔๙) อยู่ในคลัง เพราะคำถามเชิง "ถูกยกเลิก" ยังวิ่งเส้นค้นปกติ
→ **แก้แบบ general**: เติมตระกูลคำ "ถูกยกเลิก/ยกเลิกโดย" เข้าตัวจำแนกเส้น chain (`service.py`)
ให้ดึงตัวบทตามเลขมาตราตรง ๆ เหมือนคำถาม "ถูกแก้โดยใคร" → พิสูจน์ข้าม 5 มาตราที่ถูกยกเลิกโดยกฎหมาย
คนละฉบับ (5/5 — ปว.๔๙ / ฉบับที่ ๑๒ / ฉบับที่ ๑๕) + กันถอยหลังด้วย smoke test 3 ข้อ → รันซ้ำได้ **40/40**
· หมายเหตุ: ชุด v2 กับ v3 วัดแกนเดียวกันบนเนื้อหาคนละส่วน — เป็นการยืนยันซ้ำ ไม่ใช่มิติใหม่

เครื่องมือประกอบ:

- **smoke test 83 ข้อ** (`eval/smoke_test.py`) — ตรวจกติกาที่ห้ามพังโดยไม่เรียก LLM (เร็ว/ฟรี รันก่อน commit ทุกครั้ง)
  · มี regression test ที่ผูกกับบั๊กจริงที่เคยเกิด เช่น "แกะชื่อ ปว. ได้แม้ลงวันที่เดือนกุมภาพันธ์"
- **เช็ค endpoint** (`eval/check_endpoint.py`) — ดูว่า embedding/chat พร้อมใช้ไหม รันก่อนเดโม่
- **load test** (`eval/load_test.py`) — ยิง API จริงหลายคำขอพร้อมกัน ดูหัวข้อถัดไป
- ทุก run ส่งขึ้น **MLflow** เพื่อเทียบข้ามรอบได้

### 🐛 บั๊ก 4 ตัวที่เจอเพราะ "ลงมือวัด" ไม่ใช่เพราะอ่านโค้ด (5 ส.ค. 2569)

ทั้ง 4 ตัวมองไม่เห็นเลยถ้าทดสอบแบบเดิม — ต้องคุยหลายเทิร์น หรือยิงหลายคำขอพร้อมกันถึงจะโผล่

**1. การเขียนคำถามต่อเนื่องใหม่ เปลี่ยน "เส้นทาง" ของระบบได้**
```
ผู้ใช้เทิร์น 1 : ตามมาตรา ๓๑ ... ห้ามโอนภายในกี่ปี
ผู้ใช้เทิร์น 2 : โฉนดที่ดินต้องทำกี่ฉบับ            ← เปลี่ยนเรื่องแล้ว
ระบบเขียนใหม่  : โฉนดที่ดินที่ออกตามมาตรา ๓๑ ต้องทำกี่ฉบับ
                              ^^^^^^^^^^ ลากมาจากเทิร์นก่อน
```
พอมีเลขมาตราโผล่ + คำว่า "กี่ฉบับ" ที่อยู่ใน `_COMPARE_HINT` → `detect_compare` คืน `31`
→ ไหลไปเส้นเปรียบเทียบ **ตอบประวัติ ม.๓๑ แทนคำถามที่ถามจริง**
พิสูจน์: คำถามเดียวกันเป๊ะ ไม่มีประวัติ = 12 ตัวบท ตอบถูก · มีประวัติ = 3 ตัวบท ตอบผิดทั้งข้อ
→ แก้: ยืมเลขมาตราจากบทสนทนาได้ ต่อเมื่อคำถามเดิมอ้างถึงมันจริง (`_may_borrow_article`)

**2. `"กี่ฉบับ"` จับความหมายผิด — ไม่เกี่ยวกับ history เลย มีมาตั้งแต่ต้น**
"ฉบับ" ในกฎหมายไทยมีสองความหมายคนละเรื่อง: จำนวน พ.ร.บ. ที่มาแก้ กับ จำนวนใบสำเนา
`"โฉนดตามมาตรา ๕๗ ต้องทำกี่ฉบับ"` จึงไหลไปตอบประวัติ ม.๕๗ อยู่แล้วก่อนหน้านี้

**3. หลายเธรดโหลดโมเดลซ้อนกัน** — ยิงพร้อมกัน 5 คำขอตอนเซิร์ฟเวอร์เพิ่งบูต → โหลด reranker **5 ชุด**
```python
if _reranker is None:      # 5 เธรดผ่านด่านนี้พร้อมกันได้หมด
    _reranker = โหลดโมเดล   # ก่อนที่ตัวแรกจะโหลดเสร็จ
```
docstring เขียนไว้เองว่า "โหลดครั้งเดียว (lazy)" แต่จริง ๆ ไม่ใช่ · **เป็นบั๊กตระกูลเดียวกับ
`_last_mode` และ `rag.LLM_MODEL` ที่เคยเจอ — global + หลายคำขอพร้อมกัน เป็นครั้งที่ 3**
→ แก้ด้วย `RLock` 4 จุด (จุดที่หนักสุดไม่ใช่ reranker แต่คือ `_ensure_loaded` ที่อ่าน PDF 53 ไฟล์ใหม่ทั้งชุด)

**4. ตัววัด ablation เองเพี้ยน** — ให้ตัวเลขที่ดูสมเหตุสมผลแต่ผิด เกือบทำให้ถอด hybrid ทิ้ง
(รายละเอียดในหัวข้อ ablation ด้านล่าง)

### การทดลองที่จบด้วย "ไม่เปลี่ยน" — negative result ที่มีข้อมูลรองรับ

การไม่เปลี่ยนก็เป็นผลงาน ถ้าตัดสินด้วยตัวเลข ไม่ใช่ความรู้สึก — ทำมาแล้ว 4 ครั้ง
(ส่วนที่ทดลองแล้ว**เปลี่ยนจริง** อยู่ในสองหัวข้อถัดจากนี้):

**1. เปลี่ยน embedding?** (`eval/embed_compare.py`) — ลองรุ่นใหม่ 2 ตัว
วัดเฉพาะขั้นค้นหา ตัวใหม่ชนะ (28 vs 27) แต่วัดทั้งระบบ 3 รอบ ของเดิมนิ่งกว่า
(**ada 29.0 ±0.0** vs te3-large 28.3 ±0.6) → **ไม่เปลี่ยน**
_บทเรียน: อย่าเชื่อตัวชี้วัดตัวแทน ต้องวัดปลายทางจริงเสมอ_

**2. เปลี่ยนไปใช้โมเดล reasoning?** — ตอบถูกเหมือนกันแต่ช้ากว่า **7 เท่า**
(105.6s vs ~15s/ข้อ) ในเมื่อ LLM ทำหน้าที่แค่เรียบเรียง ความสามารถส่วนเกินไม่ได้ช่วย → **ไม่เปลี่ยน**

**3. เพิ่ม iterative multi-hop?** (`experiments/multihop_iterative.py`, `eval/multihop.json`)
เขียนชุดคำถาม "ต้อง hop จริง" 8 ข้อขึ้นมาก่อน เพราะชุดวัดเดิม 112 ข้อ (4 ชุดแรก) ไม่มีคำถามประเภทนี้เลย —
พอวัดแล้ว**พบช่องว่างจริง** จึงลองทำ 7 วิธี (A-G ใน `experiments/multihop_iterative.py`)
แล้วรันคำถามละ 3 รอบเพื่อวัด "ความนิ่ง":

| วิธี | ข้อ | ผ่าน | เวลา | ก้อน | นิ่ง? |
|---|---|---|---|---|---|
| iterative multi-hop (LLM คิดคำค้นเอง) | H2H1 | 1/3 | 47-72s | 20-28 | ❌ แกว่ง |
| iterative multi-hop | H2H7 | 2/3 | **29-135s** | 14-34 | ❌ แกว่ง |
| กราฟ + ชั้นเติมของ | H2H1 | 0/3 | 17-31s | **19 ทุกรอบ** | ✅ นิ่ง |
| กราฟ + ชั้นเติมของ | H2H7 | **3/3** | 16-25s | **12 ทุกรอบ** | ✅ นิ่ง |

> "กราฟ" กับ "ชั้นเติมของ" อยู่คนละระดับกัน — **กราฟคือของ 1 ชิ้น** (ตารางที่โค้ดคำนวณว่ามาตราไหน
> ถูกแก้โดยใคร) ส่วน **ชั้นเติมของคือวิธีจัดของ**: ค้นหาเสมอเป็นพื้น แล้วแปะทุกชิ้นที่เข้าเงื่อนไข
> (กราฟ · ลิงก์ refs · สรุปฉบับ · ดัชนีตัวละคร) ทับลงไป ต่างจากระบบจริงตอนนี้ที่ **เลือกทางเดียว**

คะแนนรวมเท่ากัน (3/6) แต่คุณสมบัติต่างกันสิ้นเชิง — **multi-hop ให้ผลไม่เหมือนกันสักรอบ**
คำถามเดียวกันผ่านบ้างตกบ้าง ใช้เวลา 29-135 วินาที ส่วนวิธีที่ให้โค้ดคำนวณได้ผลเดิมทุกครั้ง
เร็วกว่า **3.2 เท่า** (21.1s vs 66.8s) และใช้ token น้อยกว่า **37%** → **ไม่เพิ่ม multi-hop**

สาเหตุที่แกว่ง เห็นได้จาก log ตรง ๆ — LLM คิดคำค้นรอบสองไม่เหมือนกันสักครั้ง:
```
รอบ 1:  "อำนาจหน้าที่อธิบดีกรมที่ดิน ..."
รอบ 2:  "อำนาจหน้าที่ของอธิบดี..." + "...ของเจ้าพนักงานที่ดิน..."
รอบ 3:  "อำนาจหน้าที่เจ้าพนักงานที่ดิน..."   ← รอบนี้ไม่ค้น "อธิบดี" เลย จึงตก
```
และเมื่อใส่เบรกให้โค้ดตัดสินว่าพอหรือยัง (ไม่ได้ก้อนใหม่ = หยุด) พบว่า **LLM ไม่เคยบอกว่าพอเอง
สักครั้ง** แม้รอบ 3/4/5 จะได้ก้อนใหม่ ๐ ก้อน — ถ้าไม่ตั้งเพดานไว้คือวนไม่จบ

_บทเรียน: สิ่งที่นับได้ อย่าให้ AI เดา — หลักการเดียวกับทั้งโปรเจกต์_

ลองตั้งคำถามกับกราฟของตัวเองว่า _"มันพลาดตรงไหนได้บ้าง"_ แล้วไล่ตรวจ พบว่า regex ที่อ่าน
สายการแก้ไขเปราะกับข้อความจริงในเอกสาร **4 แบบ** ซึ่งทั้งหมด "ขาดเงียบ ๆ" โดยไม่มีอะไรฟ้อง:

| # | อาการ | สาเหตุ |
|---|---|---|
| 1 | ปว.๙๖ แกะชื่อไม่ออก (6 มาตรา) | ใช้ `[^พ]` เป็นตัวคั่น → ชนกับชื่อเดือนไทยที่มีตัว **พ** อยู่ในคำ (กุม**ภาพ**ันธ์ · **พ**ฤษภาคม · **พ**ฤศจิกายน) |
| 2 | ปว.๓๓๔ แกะไม่ออกในฉบับที่ ๑๔ | เอกสารเขียน "ประกาศคณะปฏิวัติ" (ไม่มี "ของ") + "พุทธศักราช" (ไม่ใช่ "พ.ศ.") |
| 3 | ชื่อ พ.ร.บ. แกะไม่ออก (ม.๘๑, ๑๐๕) | PDF ตัดบรรทัดกลางคำ → normalize แล้วเหลือ "ประมวล กฎหมาย ที่ดิน" มีช่องว่างแทรก |
| 4 | **ยกชื่อฉบับผิดมาตรา** | ท้าย clause จับแบบ greedy จึงกลืน clause ถัดไปทั้งอัน |

**ข้อ 4 หนักที่สุด เพราะไม่ได้แค่ไม่รู้ แต่ตอบผิด:**
```
ข้อความจริงในฉบับที่ ๓:
  "มาตรา ๓ ให้ยกเลิกมาตรา ๗ ...   มาตรา ๔ ให้ยกเลิกความในมาตรา ๒๐ ... ซึ่งแก้ไขเพิ่มเติมโดย ปว.๙๖"
                                                                       └──── เป็นของ ม.๒๐ ────┘
ก่อนแก้:  ม.๗ ได้ ปว.๙๖ ของ ม.๒๐ มาใส่   ·  ม.๒๐ หายจากกราฟไปทั้งมาตรา
หลังแก้:  ม.๗ = ตัวบทเดิม ๒๔๙๗           ·  ม.๒๐ = ปว.๙๖ → ฉ.๓ → ฉ.๑๔
```
แก้ด้วย tempered token `(?:(?!<หัว clause>)[^“]){0,400}` — เดินทีละตัวอักษรแต่หยุดทันทีที่เจอ clause ใหม่

**ผลรวม:** สายที่แกะชื่อไม่ออก **10 มาตรา → 0** · เทียบสายทั้ง 34 มาตราก่อน/หลัง เหมือนเดิม 29
แก้ให้ถูก 5 ไม่พังสักอัน · `run_eval` 29/30 เท่าเดิม · เพิ่ม regression test 10 ข้อ

_บทเรียน: บั๊กที่ไม่มี error ให้เห็นคือบั๊กที่อยู่ได้นานที่สุด — ต้องมี test ที่ถามว่า
"ยังเหลืออะไรที่อ่านไม่ออกไหม" ไม่ใช่แค่ test ที่ถามว่า "ตัวอย่างนี้ถูกไหม"_

### ดัชนีตัวละคร — ปิดคำถามแบบ "รวบรวมให้ครบ" ที่การค้นทำไม่ได้โดยธรรมชาติ

คำถาม H2H1 _"ผู้มีอำนาจสั่งเพิกถอนโฉนด ยังมีอำนาจอื่นใดอีก"_ ตก **0/3 ทุกวิธี** พอไล่หาสาเหตุ
พบว่า**ไม่ใช่ปัญหาการ hop**:

```
คำว่า "อธิบดี" อยู่ใน 13 มาตรา   แต่ระบบดึงได้ทีละ 12 ก้อน (ซ้ำมาตราเดิมด้วย)
```
การค้นเรียงตาม **"ความคล้าย"** ไม่ใช่ **"ความครบ"** — ค้นซ้ำกี่รอบก็ไม่ครบ เพราะเป็นคนละงานกัน

**ทางแก้ (`rag.entity_index`)** — ให้โค้ดกวาดนับตอนสร้างดัชนีว่า entity ไหนอยู่มาตราใดบ้าง
แล้วตอนตอบก็แปะรายชื่อ + ตัวบทจริงของมาตราเหล่านั้นเข้า context

| | ก่อน | หลัง |
|---|---|---|
| ตัวบทที่โค้ดคำนวณข้อเท็จจริงได้เอง | 34/131 (25%) | **69/131 (52%)** |
| H2H1 | 0/3 | **2/3** |

**2 จุดที่ทำผิดตอนแรกแล้วแก้** (เขียนคอมเมนต์กันพลาดซ้ำไว้ในโค้ดแล้ว):
1. **เลือก entity จากคำถามอย่างเดียว** → ได้ "โฉนดที่ดิน" ซึ่งเป็น*กรรม* ไม่ใช่*ประธาน*
   คำถามจริงมักบรรยายตัวละครแทนที่จะเรียกชื่อ ต้องดูตัวบทที่ค้นได้ด้วย และนับ*จำนวนครั้ง*
   ไม่ใช่แค่เจอ/ไม่เจอ (ประธานของมาตราถูกเอ่ยซ้ำกว่าตัวประกอบ)
2. **ดึงตัวบทจาก chunk ที่ใช้ค้น** → ม.๕๑ ๕๔ ๙๑ ๙๘ ได้ศูนย์ก้อน และ ม.๒๗ ได้เศษกลางมาตรา
   เพราะ chunk หั่นตาม*ความยาว* ไม่ได้หั่นตาม*มาตรา* — ต้องดึงจาก `doc_articles()` ซึ่งเป็น
   แหล่งเดียวกับที่ใช้สร้างดัชนี

**และวัดผลก่อนต่อเข้าระบบจริง แล้วเจอว่ามันทำของเดิมพัง:**
```
F (ไม่มีดัชนีตัวละคร)  13/14        G (มีดัชนีตัวละคร)  11/14   ← H1 กับ H10 ที่เคยผ่าน กลายเป็นตก
```
สาเหตุ: `"ฉบับใดบ้าง"` / `"มาตราใดบ้าง"` ก็ติดเงื่อนไข "ถามแบบครบถ้วน" เหมือนกัน แต่เป็นคำถาม
เรื่อง*การแก้ไข* ไม่ใช่เรื่อง*ตัวละคร* — ชั้นตัวละครเลยเอาตัวบท 24 มาตรา (~21,000 ตัวอักษร)
ไปกลบสายการแก้ไขที่กราฟเตรียมไว้ให้เรียบร้อยแล้ว **แก้โดยให้ชั้นเจาะจงมาก่อนชั้นกว้างเสมอ**
→ กลับมา **13/14 เท่า F แล้วได้ H2H1 เพิ่มมา**

_บทเรียน: "เติมของเผื่อไว้ให้เยอะที่สุด" ไม่ใช่กลยุทธ์ที่ดี — ของกว้างจะกลบของเจาะจง
และวิธีเลือกว่าต้องวัดข้อไหน: ชั้นนี้มีประตูคุมอยู่ จึงมีแค่ 14/120 ข้อที่ผลเปลี่ยนได้
อีก 106 ข้อโค้ดเดินเส้นเดิมทุกบรรทัด → รัน 30 นาที แทน 5 ชั่วโมง_

**4. แก้ prompt เพื่อดัน H2H1 ให้เป็น 3/3?** — พอวัดจนรู้ว่าคอขวดอยู่ที่การเรียบเรียงคำตอบแล้ว
(context เหมือนกันเป๊ะทั้ง 3 รอบ แต่ผลต่างกัน) ก็ลองแก้ที่ต้นเหตุตรง ๆ เติมกฎเข้า `SYSTEM_PROMPT`
สองข้อ: (ก) ถ้าถามถึงสิ่ง "อื่น/นอกเหนือจาก" คำตอบต้องมาจาก**มาตราอื่น** ห้ามตอบด้วยวรรคย่อย
ของมาตราเดิม (ข) ถ้า context มีบล็อกที่โค้ดนับมาให้ครบแล้ว ให้ยึดรายการนั้นเป็นขอบเขตคำตอบ

```
H2H1      2/3  →  2/3      (รอบที่ตกยังขาดคำเดิมเป๊ะ: "จำหน่าย", "จัดที่ดิน")
eval 30   29/30 → 29/30    (ไม่ทำของเดิมพัง แต่ก็ไม่ได้ช่วย)
```
→ **ไม่ต่างทั้งสองทาง จึง revert ออก** · การเก็บกฎที่พิสูจน์ไม่ได้ว่าช่วยไว้ใน prompt
คือการสะสมความรก แล้วครั้งหน้าจะแยกไม่ออกว่ากฎข้อไหนมีผลจริง

_บทเรียน: รู้ว่าคอขวดอยู่ตรงไหน ≠ แก้ตรงนั้นแล้วจะได้ผล · ปัญหานี้น่าจะต้องแก้ด้วยวิธีอื่น
(เช่นบีบให้ตอบเป็นโครงสร้างที่ตรวจได้ แทนการบอกเป็นข้อความให้ LLM ทำตาม) และ 3 รอบ
ก็ยังเป็นตัวอย่างที่น้อยเกินกว่าจะแยก 2/3 กับ 3/3 ออกจากกันได้อย่างมั่นใจ_

### ให้โค้ดตรวจ "คำตอบ" ไม่ใช่แค่เตรียม "ข้อมูล" — ปิด H2H1 ได้ 3/3

ต่อจากผลทดลองที่ 4: ในเมื่อ "ขอเป็นข้อความ" ไม่ได้ผล ก็ลองเปลี่ยนเป็น **"บังคับเป็นโครงสร้าง"**
(`experiments/multihop_iterative.py` วิธี H) — เพิ่ม 3 ขั้นต่อจากดัชนีตัวละคร:

```
① บังคับ LLM สกัดเป็น JSON     (endpoint รองรับ response_format — เช็คแล้ว)
② โค้ดเทียบกับ entity_index    ขาดมาตราไหน -> ขอใหม่พร้อมชี้ตัวที่ขาด
③ หลังเรียบเรียงเป็นข้อความ     โค้ดเช็คว่าตกหล่นไหม -> ตกก็เติมกลับ
```

**ขั้น ③ คือตัวชี้ขาด** — ทำแค่ ①② ยังได้ 2/3 เท่าเดิม เพราะปัญหาไม่ได้อยู่ที่ "อ่านไม่ครบ"

```
รอบ    ①② อ่านครบไหม      ③ เขียนครบไหม
 1     ✅ ครบ              ตกหล่น  4/12
 2     ✅ ครบ              ตกหล่น  3/11
 3     ✅ ครบ              ตกหล่น 11/12   ← รอบที่เคยตก
 4     ✅ ครบ              ตกหล่น  4/13
 5     ✅ ครบ              ตกหล่น  5/13
```
LLM ได้โครงครบทุกรอบ ถูกสั่งว่า "ห้ามตัดทิ้ง" ทุกรอบ **แต่ก็ตัดทุกรอบ** — และรอบที่ตัดเยอะ
ใช้เวลา 30 วินาที ขณะที่รอบที่เขียนครบใช้ 70-78 วินาที คือมันเขียนสั้นลงแล้วข้ามของ
(เจอพฤติกรรมเดียวกันที่ข้อ V35 ด้วย ตกหล่น 10/11 → ไม่ใช่เรื่องเฉพาะข้อ H2H1)

| | H2H1 | 14 ข้อที่ได้รับผลกระทบ |
|---|---|---|
| ชั้นเติมของ (F) | 0/3 | 13/14 |
| + ดัชนีตัวละคร (G) | 2/3 | 13/14 |
| **+ ตรวจคำตอบ (H)** | **5/5** | **41/42** (รัน 3 รอบ) |

**ยังไม่นิ่ง 100%** — H2H2 ได้ 2/3 เพราะคำถามอ้างถึงฉบับแก้ไขแบบอ้อม (_"ฉบับเดียวกับที่แก้ไข
มาตรา ๖๑ ครั้งล่าสุด"_) ประตู "ชั้นเจาะจงมาก่อน" จึงจับไม่ได้ แยกไปแก้ต่างหาก

_บทเรียน: เดิมโค้ดทำงานแค่ **ก่อน** LLM ตอบ (เตรียมข้อมูลให้ครบ) แล้วเชื่อว่า LLM จะใช้ครบ —
วัดแล้วพบว่าไม่จริง จึงต้องตรวจ **หลัง** ด้วย · LLM ยังเป็นคนเขียนอยู่ แค่ไม่ได้เป็นคนตัดสิน
ว่าอะไรควรถูกตัดทิ้ง_

### BM25 สำรองเมื่อ embedding ล่ม

`embedding` ยิงไป endpoint ภายนอกจึงล่มได้ (เคยเกิดจริง — โควตาหมด ตอบอะไรไม่ได้ครึ่งวัน)
เดิมล่มแล้ว**เส้นค้นตายทั้งเส้น** ทั้งที่ BM25 คำนวณในเครื่องและยังทำงานได้อยู่

วัดก่อนว่าโหมดสำรองคุ้มค่าทำไหม (ชุดหลัก 30 ข้อ · คำถามขยาย 4 มุมเหมือนระบบจริง · เปิด rerank):
```
BM25 อย่างเดียว      26/30      ← ใช้งานได้จริง ไม่ใช่แค่ประคอง
semantic อย่างเดียว  26/30
hybrid (ปกติ)        26/30
```
BM25 อย่างเดียวได้เท่ากับตอนครบสองสาย — โหมดสำรองจึงไม่ใช่แค่ "ดีกว่าไม่มีอะไรเลย"
แต่**ตอบได้เกือบเท่าปกติ** บนชุดคำถามนี้ (ดูรายละเอียดในหัวข้อ ablation ด้านล่าง)

ตอนนี้ `rag.retrieve` จับ error แล้วสลับไป BM25 อย่างเดียว พร้อม**แจ้งผู้ใช้ 3 ทาง**
(event stage · `meta.retrieval_mode` · ป้ายคาดหัวตัวคำตอบ) — เพราะการลดคุณภาพแบบเงียบ ๆ
คือบั๊กตระกูลเดียวกับที่ใช้เวลาไล่จับนานที่สุด

> ⚠️ **2 จุดที่เขียนพลาดตอนแรก** (บันทึกไว้กันพลาดซ้ำ):
> **1.** เก็บโหมดไว้ใน global — แต่ `retrieve` รันในเธรดแยกและ FastAPI รับหลายคำถามพร้อมกันได้
> คำถามที่ปกติจะไปทับค่าของคำถามที่ล่ม แล้วคนนั้นไม่ได้รับคำเตือน → เปลี่ยนเป็นส่งออกทาง `stats=`
> **2.** ดัก error ด้วย `(ConnectionError, TimeoutError, OSError)` แล้ว**เทสผ่าน** เพราะเทสจำลอง
> ด้วย `ConnectionError` — แต่ error จริงสืบทอดจาก `openai.OpenAIError` ไม่ใช่ `ConnectionError`
> เลย (ตรวจแล้วทั้ง `APIConnectionError`/`RateLimitError`/`AuthenticationError`) แปลว่าของจริง
> ล่มแล้วระบบก็ยังพังเหมือนเดิม → เทสตอนนี้เช็คกับ**คลาส error ตัวจริง** ไม่ใช่ตัวที่เราจำลองขึ้นเอง

_บทเรียน: เทสที่จำลองด้วย error คนละตัวกับของจริง คือเทสที่ผ่านแต่ไม่ได้พิสูจน์อะไร_

### 🔬 "รวมสองสายแล้วดีกว่า" จริงไหม — วัดผิดรอบแรก แล้ววัดใหม่

ระหว่างทำ BM25 fallback เลยวัดเทียบไปด้วยว่าแต่ละสายเก่งแค่ไหน
(`experiments/hybrid_ablation.py` · ปิดสายใดสายหนึ่งได้ โดยไม่แตะโค้ดจริง)

**รอบแรกสรุปว่า "hybrid แย่กว่า BM25 อย่างเดียว" — แล้วปรากฏว่าตัววัดเองเพี้ยน**

```
                        semantic   BM25   hybrid
รอบแรก (ผิด)              22/30   24/30   21/30    ← เคยเขียนไว้ใน README
คำถามดิบ + สำเนาที่แก้แล้ว   24/30   26/30   25/30
คำถามขยาย 4 มุม = ระบบจริง   26/30   26/30   26/30   ← ตัวเลขที่อ้างได้
```

รอบแรกผิด 2 ชั้น — สำเนาลอจิก**ขาดขั้นดันอันดับทั้งสองตัว** (`_boost_amend`,
`_boost_exact_article` ซึ่งเป็นกลไกหลักเวลาถามเจาะมาตรา) และใช้คำถามดิบแทนคำถามที่ขยายแล้ว
ตอนนี้สคริปต์มี `verify_copy()` เทียบผลกับ `rag.retrieve` จริงก่อนวัดทุกครั้ง ไม่ตรงจะหยุดทันที

**ผลจริง: บนข้อมูลชุดนี้ เลือกสายไหนแทบไม่ต่างกันเลย** เพราะ reranker กับขั้นดันอันดับ
ทำงานหนักกว่าชั้นค้นมาก ขอแค่ตัวบทที่ถูกติดเข้ามาใน pool 48 ก้อน ที่เหลือสองขั้นนั้นจัดการเอง
(ตรวจแล้วว่า 8 ใน 10 ข้อได้ chunk คนละชุดจริง — ไม่ใช่โค้ดแยกโหมดไม่ออก)

**ปัญหา RRF เบียดกันมีจริง แต่หายไปเมื่อขยายคำถาม**
```
อยู่อันดับ 1 สายเดียว      = 1/(60+0)  = 0.01667
อยู่อันดับ 10 ทั้งสองสาย   = 2/(60+9)  = 0.02899   ← ชนะ
```
เห็นผลตอนใช้คำถามดิบ (H4, H9 หาเจอด้วยสายเดียว แต่ตกตอนรวมสาย) พอขยายเป็น 4 มุม
= 8 รายการอันดับ ตัวบทที่ถูกจะสะสมคะแนนข้ามมุมจนขึ้นมาได้เอง **อาการนี้ไม่เหลือเลย**

_บทเรียนที่แพงที่สุดของการทดลองนี้: ตัววัดที่ลอกลอจิกมาไม่ครบ ให้ตัวเลขที่ดูสมเหตุสมผล
และเกือบทำให้ตัดสินใจถอด hybrid ทิ้ง — เครื่องมือวัดต้องมีตัวตรวจว่ามันวัดถูก
ไม่ใช่เชื่อว่าลอกมาถูกแล้ว_

### MLflow Tracing — เปิดดู "วิธีคิด" ของระบบได้ทุกคำถาม

ตั้ง `RAG_TRACE=1` แล้วทุกคำถาม (หน้าเว็บ / API / eval) จะถูกบันทึกเส้นทางหาคำตอบเป็นต้นไม้
1 คำถาม = 1 trace ขึ้น MLflow (แท็บ Traces) — คลิกแต่ละกล่องเห็น input/output จริงของขั้นนั้น:

```
answer_stream 49.1s              ← รากเดียวต่อคำถาม
├─ detect_compare                ← จำแนก: เข้าเส้นเปรียบเทียบ/ประวัติมั้ย
├─ pick_groups                   ← กฎในโค้ดเลือกกลุ่มเอกสาร/ปี/เวอร์ชัน
├─ expand_queries 1.7s           ← LLM แตกคำถามเป็น 4 มุมค้นหา
├─ retrieve 45.1s
│   ├─ search_q1..q4             ← ต่อมุม: semantic top-5 vs BM25 top-5
│   ├─ rrf_fuse                  ← อันดับหลังรวมคะแนนทุกมุม
│   └─ rerank                    ← cross-encoder คัด 50 → 12
└─ invoke_retry 2.1s             ← prompt เต็มที่ LLM เห็น + คำตอบดิบ
```

คำถามเชิงประวัติ (เช่น _"มาตรา ๙ ถูกแก้กี่ครั้ง"_) จะเห็นอีกทรง: `article_timeline` + `article_chain`
ตอบจบใน ~7 วินาที**โดยไม่แตะ embedding/BM25/rerank เลย** — หลักฐานเป็นภาพของแนวคิด
"ข้อเท็จจริงให้โค้ดคำนวณ การเรียบเรียงให้ LLM" · ปิดสวิตช์ (ค่าเริ่มต้น) = ไม่มี overhead ใด ๆ

## ข้อจำกัดที่รู้ตัว

เขียนไว้ตามจริง — ของพวกนี้ยัง**ทำไม่ได้** ณ ตอนนี้:

**เรื่องข้อมูล**
- **ปว.๓๓๔ และ ปว.๙๖ ไม่มีตัวบทในคลัง** (รวม 15 มาตราที่มีต้นสายเป็นสองฉบับนี้) — ระบบ*รู้ชื่อ*
  เพราะตัวบทฉบับหลังอ้างถึง และตอบได้ว่า "ต้นสายคือฉบับนี้" แต่**ตอบไม่ได้ว่าเนื้อหาเดิมเขียนว่าอะไร**
  โค้ดติดป้าย `in_corpus: False` แล้วสั่งห้าม LLM แต่งเนื้อหาขึ้นเอง
- ฉบับสแกน (`*_ImgPDF.pdf`) ผ่าน OCR จึงมีคำเพี้ยนได้ — ถูกดันไปท้ายอันดับด้วย `RAG_SCAN_DEMOTE`
  และไม่ถูกใช้สร้างกราฟเลย (ใช้คู่แฝด TruePDF แทน)

**เรื่องการหาคำตอบ**
- **คำถามที่ไม่มีเลขมาตราจะไม่เข้าเส้นกราฟ** — ถาม _"มาตรา ๖๑ ถูกแก้กี่ครั้ง"_ เข้า แต่ถาม
  _"กฎหมายเรื่องเพิกถอนโฉนดเปลี่ยนไปยังไง"_ ตกไปเส้นค้นปกติ ซึ่งผู้ใช้จริงมักไม่รู้เลขมาตรา
- **เส้นกราฟยัง "ข้ามการค้นทั้งหมด"** — คำถามที่ถามสองเรื่องพร้อมกัน (_"ม.๖๑ ถูกแก้กี่ครั้ง
  และปัจจุบันใครมีอำนาจเพิกถอน"_) จะได้คำตอบเรื่องเดียว · แบบ "ชั้นเติมของ" ที่ค้นเสมอแล้วแปะ
  กราฟทับ ทำไว้ใน `experiments/` แล้วและวัดผลแล้ว แต่**ยังไม่ได้ย้ายเข้าระบบจริง**
- **ดัชนีตัวละครยังอยู่แค่ใน `experiments/`** — `rag.py` มีฟังก์ชันแล้วแต่ยังไม่มีใครใน
  `service.py` เรียก รอวัดกับชุดคำถามเต็มก่อน
- **~~ไม่มีทางสำรองเมื่อ embedding ล่ม~~ — แก้แล้ว** ตกไปใช้ BM25 อย่างเดียวพร้อมแจ้งผู้ใช้
  · แต่โหมดสำรองมีจุดอ่อนคนละแบบ: ถ้าผู้ใช้ใช้คำต่างจากตัวบท (_"บุกรุก"_ vs
  _"เข้าไปยึดถือครอบครอง"_) จะหาไม่เจอ แล้วตอบว่า "ไม่พบข้อมูล" ทั้งที่มี
- **~~chat LLM ล่ม = ตอบไม่ได้เลย~~ — แก้แล้ว** คืนตัวบทที่ค้นเจอ 6 อันดับแรกให้อ่านเอง
  พร้อมป้ายบอกชัดว่ายังไม่ได้เรียบเรียงและไม่ได้ตรวจ · งานที่ค้นมาแล้วไม่ถูกทิ้งเพราะขั้นสุดท้ายพัง
- **~~ไม่มี `pythainlp` แล้ว BM25 เสื่อมเงียบ ๆ~~ — แก้แล้ว** `/health` รายงาน `tokenizer`
  และเปลี่ยน `status` เป็น `degraded` · ผู้เรียกควรมอนิเตอร์ `status` ไม่ใช่แค่ HTTP 200
- **~~คำถามต่อเนื่องหลายเทิร์นยังไม่เคยวัดผล~~ — วัดแล้ว** `eval/multiturn.json` 6 บทสนทนา
  (ข้อจำกัดที่เหลืออยู่ในหัวข้อถัดไป)

**เรื่องที่วัดแล้วรู้ว่ายังไม่ดีพอ**
- **การเรียบเรียงคำตอบยังแกว่ง** — H2H1 ได้ 2/3 โดยที่ context เหมือนกันเป๊ะทั้ง 3 รอบ
  (19 ก้อน · 24 มาตรา · ±0.0) แปลว่าฝั่งค้นนิ่งแล้ว ที่เหลือเป็นเรื่อง LLM ประกอบคำตอบ
- **คำถามต่อเนื่อง: ตอนผู้ใช้เปลี่ยนเรื่องกลางบทสนทนายังไม่นิ่ง** — ระบบอาจลากหัวข้อเดิม
  มาปนคำถามใหม่ (ราว 1 ใน 2 รอบ) เพราะการเขียนคำถามใหม่เป็นการเรียก LLM
  แก้ prompt ช่วยได้แต่ไม่รับประกัน · **ตัวกันเส้นทางที่ใส่ไว้ทำงานทุกรอบ** ผลจึงเหลือแค่
  "ตอบไม่ครบ" ไม่ใช่ "ตอบผิดเรื่อง" — ถ้าจะถามเรื่องใหม่ ส่ง `history: []` จะแม่นกว่า
- **ยิงพร้อมกันเกิน 5 คำขอแล้วพัง** — ที่ 8 คำขอแต่ละคนรอนานขึ้น 6 เท่า ควรจำกัดที่ 3
- **มีคีย์ API เดียวใช้ร่วมกันทุกคน** — แยกไม่ออกว่าใครยิงมา และไม่มีการจำกัดจำนวนคำขอ
- ระบบให้คะแนน eval เป็น key-fact matching ไม่ใช่คนตรวจ — จับ "ตอบครบไหม" ได้ดี
  แต่จับ "เรียบเรียงดีไหม" ไม่ได้ · และแยกไม่ออกระหว่าง "ตอบไม่ครบ" กับ "เฉลยถามเกินคำถาม"
  (ดู E5/H10) — **ข้อที่ตกต้องอ่านคำตอบจริงประกอบเสมอ**

```powershell
python -m venv .venv
.venv\Scripts\activate
```
